You are building a stand-alone Complaint & Dispute Management platform as a single-repo Replit project using TypeScript, Next.js (App Router) for the UI, and an Express API in the same repo. Use a config-driven architecture (no hardcoded categories/checklists). Optimize for Replit constraints (ephemeral FS, limited background workers, no Redis by default).

0) Tech baseline (Replit-friendly)

Single repository, not a monorepo.

Frontend: Next.js (App Router), React Query, Zod, Tailwind, shadcn/ui.

Backend: Express + TypeScript (in /api folder or custom server under /server).

ORM/DB: Prisma. Dev: SQLite if DATABASE_URL absent. Prod-ready: Postgres when DATABASE_URL present.

Env: .env.local with typed access. Provide .env.example.

Testing: Vitest for units; Playwright later for e2e.

Lint/format: ESLint + Prettier.

Health: /healthz (web) and /api/healthz (API).

1) Functional goal (from workflow doc)

Build a system to intake and resolve Mail, Complaint, and Dispute cases with:

Universal fields (customer, loan, state, details, priority, etc.).

Branching checklists by Case Type → Category, with required uploads/flags.

Resolution module (disposition, sub-disposition, settlement, policy violation, etc.).

Priority rules (e.g., Critical for AG/CFPB/Military/Search Warrant/Subpoena/Suspected ID Theft; High for BBB/BCA/C&D/Lawsuit/Loan Dispute/Private Attorney/Verbal/Written; Medium for Viking POA/FactorTrust/PDS/ACH Revoke; Low for E-Fax/Misc; BK-specific 24/48 hr SLAs). These must be admin-editable, not hardcoded.

Flags/Tags (e.g., Do Not Contact, Complaint-Regulatory, Fraud Trigger Words), applied by rules.

Documents (loan agreement, police report, POA, etc.) with S3 presigned upload/download.

Audit trail, dashboards, and admin config panel to add/edit categories, checklists, rules, and value sets without code.

2) Data model (Prisma schema)

Create these runtime tables (simplified names → camelCase fields):

User (id, email unique, name, role: ‘agent’|‘compliance’|‘admin’, status, createdAt, updatedAt)

Customer (id, externalId?, name, state, createdAt, updatedAt)

Case (id, caseType: ‘Mail’|‘Complaint’|‘Dispute’, categoryId FK, priority: ‘Low’|‘Medium’|‘High’|‘Critical’|‘BK24’|‘BK48’, customerId FK, loanId?, state, details text, status: ‘open’|‘pending’|‘resolved’|‘closed’, configVersion int, createdAt, updatedAt)

ChecklistItem (id, caseId FK, key, label, isRequired bool, status: ‘open’|‘complete’, assignedToUserId?, completedAt?)

Document (id, caseId FK, key, label, fileType, mime, storageKey, uploadedByUserId FK, uploadedAt)

Resolution (id, caseId FK unique, disposition, subDisposition?, notes?, settlementAmount decimal?, forgivenAmount decimal?, policyViolation: ‘Yes’|‘No’|‘N/A’, resolvedAt)

Flag (id, caseId FK, flagType, appliedByUserId FK, appliedAt)

AuditLog (id, caseId FK, actorUserId?, action, details json, createdAt)

Create these admin-config tables (no hardcoding; versionable):

CaseType (id, name, isActive)

Category (id, caseTypeId FK, name, code, description, sortOrder int, isActive, version int, effectiveFrom, effectiveTo?)

ChecklistTemplate (id, categoryId FK, key, label, sortOrder int, isRequired bool, conditionJson json, helpText?)

DocumentRequirement (id, categoryId FK, key, label, isRequired bool, mimeWhitelist string[], conditionJson json)

PriorityRule (id, categoryId FK, ruleJson json, priorityValue string)

TagRule (id, categoryId FK, ruleJson json, tags string[])

ResolutionConfig (id, categoryId FK, fieldsJson json)

SlaPolicy (id, categoryId FK, targetHours int, clockStartsOn string, pauseOnStatus string[])

ValueSet (id, key unique, valuesJson json) // e.g., US states, dispositions

ConfigAudit (id, userId FK, entity, entityId, action, beforeJson json, afterJson json, createdAt)

FeatureFlag (id, key unique, on bool, audienceJson json)

Webhook (id, name, eventKey, url, secret?, isActive, createdAt, updatedAt)

Integration (id, name, settingsJson json, isActive, createdAt, updatedAt)

Relations/Indexes:

Case→Customer (many:1), Case→Category (many:1).

Children (ChecklistItem, Document, Resolution, Flag, AuditLog) → Case (many:1).

Indexes on Case(caseType, categoryId, priority, status, createdAt, customerId, loanId).

Unique: Resolution(caseId).

Use soft disable isActive in config tables; avoid hard deletes.

Case.configVersion pins the config snapshot used at creation.

4) API endpoints (Express, JSON)

Cases: POST /api/cases (create; assign configVersion), GET /api/cases/:id, PUT /api/cases/:id, GET /api/cases (filters: status, priority, type, category, state, date range, text).

Checklist: GET /api/cases/:id/checklist (materialize from templates into per-case items on first fetch), PUT /api/checklist/:itemId (toggle complete/assign).

Documents: POST /api/cases/:id/documents/presign (S3 presigned upload), GET /api/cases/:id/documents (list with presigned download).

Resolution: POST /api/cases/:id/resolution (validate required items/docs, then lock case), GET /api/cases/:id/resolution.

Flags/Notes/Audit: POST /api/cases/:id/flags, GET /api/cases/:id/audit, POST /api/cases/:id/notes.

Config (admin): CRUD endpoints for all config tables; POST /api/admin/config/publish (snapshot current config into a new version; bump version; write ConfigAudit); POST /api/admin/config/cache/flush.

Config read: GET /api/config/latest, GET /api/config/version/:v, GET /api/value-sets/:key.

Health: /api/healthz.
